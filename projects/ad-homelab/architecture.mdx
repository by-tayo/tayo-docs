Two separate design decisions shape this lab: how the network isolates domain traffic, and how the directory itself is organized once it exists.

## Network Design

Rather than having the domain controller run Routing and Remote Access with NAT (a pattern common in other AD homelab guides), this build lets VMware Workstation handle isolation and internet access directly, through two separate virtual networks:

<CardGroup cols={2}>
  <Card title="VMnet1 — Host-only" icon="network-wired">
    `192.168.125.0/24`, DHCP disabled. Carries all domain traffic between DC01 and future domain-joined machines. Fully isolated from the home network.
  </Card>

  <Card title="VMnet8 — NAT" icon="globe">
    VMware-managed NAT, DHCP-assigned. Gives each VM independent internet access for updates and activation, with no dependency on the DC for routing.
  </Card>
</CardGroup>

Every lab VM gets **two** adapters: one on `VMnet1` with a static IP, and one on `VMnet8` for outbound internet access. DNS on the `VMnet1` adapter points at DC01 itself (`127.0.0.1` on the DC, `192.168.125.10` on everything else), since DC01 runs AD-integrated DNS.

```text
DC01            192.168.125.10   (VMnet1, static)  +  NAT adapter (VMnet8, DHCP)
CLIENT01 *       192.168.125.11   (VMnet1, static)  +  NAT adapter (VMnet8, DHCP)
LOGSRV *         192.168.125.12   (VMnet1, static)  +  NAT adapter (VMnet8, DHCP)
ATTACKER (Kali)  192.168.125.13   (VMnet1, static)  +  NAT adapter (VMnet8, DHCP)

* planned, not yet built
```

<Tip>
  DHCP is deliberately disabled on `VMnet1`. Every machine on the domain network gets a static IP assigned by hand — with only a handful of VMs, this avoids any chance of DHCP handing out an address that collides with one already in use.
</Tip>

## Why Not DC-Based NAT?

Having the domain controller itself act as gateway, DHCP server, and NAT router (via the Routing and Remote Access role) is a well-known pattern, but it adds three extra roles' worth of failure surface to troubleshoot before the domain is even usable. Letting VMware own the NAT and isolation boundary keeps the DC focused on what it's actually there to demonstrate — AD DS, DNS, OU/GPO design — and makes networking failures immediately distinguishable from AD failures.

## Directory Structure

The OU tree is built to mirror a small-to-mid-size organization rather than a flat, default install:

```text
corp.lab
└── Corp
    ├── IT
    │   ├── Users
    │   ├── Groups     (IT-Staff)
    │   └── Computers
    ├── Finance        (Finance-Staff)
    ├── Sales          (Sales-Staff)
    ├── HR             (HR-Staff)
    ├── Marketing      (Marketing-Staff)
    ├── Engineering    (Engineering-Staff)
    ├── Operations     (Operations-Staff)
    ├── Support        (Support-Staff)
    └── Helpdesk group (top-level, for delegated password-reset rights)
```

Each department OU has its own `Users`, `Groups`, and `Computers` sub-OUs, and its own `<Department>-Staff` security group. A top-level `Helpdesk` group exists separately, scoped for a single delegated permission (password resets) rather than broad admin rights — the point being to demonstrate least-privilege delegation, not just run everything as Domain Admin.

How this structure gets built — entirely via PowerShell rather than manually clicking through Active Directory Users and Computers — is covered on the [Configuration](/projects/ad-homelab/configuration) page.
