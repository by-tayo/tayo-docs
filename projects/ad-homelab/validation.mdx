## Confirmed Working

| Item | Verification |
| --- | --- |

| Host-only network isolation | `VMnet1` static addressing confirmed, no cross-talk with the home network |
| pfSense routing | `ping` to the gateway (`192.168.125.254`) and to `8.8.8.8` returns 0% packet loss from both DC01 and CLIENT01 |
| OU tree and department groups | 8 departments, each with `Users`/`Groups`/`Computers` sub-OUs and a `-Staff` group, built via `setup-ou-structure.ps1` |
| Bulk user provisioning | 1,050 accounts created, 0 skipped, verified via `Get-ADUser -Filter * -SearchBase 'OU=Corp,DC=corp,DC=lab' \| Measure-Object` |
| Help-desk delegation | `Reset user passwords` permission delegated to the `Helpdesk` group on the `IT` OU |
| Client join | `CLIENT01` (Windows 11, local-account-only) built, given a static IP, and joined to `corp.lab` — confirmed via System Properties showing `Domain: corp.lab` and the computer object appearing in ADUC's default `Computers` container |
| Client hostname aligned with lab naming | `CLIENT01` renamed from its Windows-assigned default (`DESKTOP-HNA8DUJ`) to `CLIENT01` — confirmed as the reporting `host` value in Splunk after the rename |
| Security telemetry pipeline | Sysmon (SwiftOnSecurity config) deployed on DC01 and `CLIENT01`, Splunk Universal Forwarder installed on both, indexed by Splunk Enterprise on LOGSRV — verified end-to-end with `index=main \| stats count by host` (4,393\+ events from DC01, 318\+ from `CLIENT01`, 1,962 of them Sysmon process-creation events) |
| GPO — Interactive logon banner | Linked to `CLIENT01`'s OU, banner text confirmed showing on the Windows sign-in screen after `gpupdate /force` and a reboot |
| GPO — Desktop wallpaper via UNC | `\\DC01\Wallpaper` share applied through a User Configuration policy with **Loopback Processing (Merge mode)** enabled so it applies on the Computers OU — `gpresult /r` on `CLIENT01` confirms the policy is being applied |
| GPO — Prohibit access to Control Panel and PC Settings | Restriction confirmed by the **Restrictions** block dialog popping up when opening Control Panel or Settings on `CLIENT01` |
| Kali attacker VM on the lab network | Existing Kali VM re-homed onto `VMnet1`, DHCP address `192.168.125.101` from pfSense — connectivity to the gateway, the internet, and `nslookup corp.lab` against DC01 all confirmed |
| BloodHound CE installed on Kali | BloodHound Community Edition deployed via Docker Compose (Postgres app-db, Neo4j graph-db, and the BloodHound app), web UI reachable at `http://localhost:8080` |
| Domain enumeration with BloodHound | `bloodhound-ce-python` run remotely over LDAP as `jsmith` — collected 1,030 users, 61 groups, 5 GPOs, 34 OUs, 19 containers, 2 computers (DC01 \+ `CLIENT01`), 0 trusts; `.zip` uploaded into BloodHound and processed successfully |
| Baseline attack-path check | Cypher shortest-path query from `jsmith` to `Domain Admins` returns **no path**; `MATCH (u:User {hasspn:true})` returns **none** — the expected clean baseline before any misconfiguration is introduced |
| Deliberately vulnerable service account | `svc_sql` created in the `IT` OU with a weak password (`Summer2024!`) and `MSSQLSvc/dc01.corp.lab:1433` registered via `setspn -S` — visible to `bloodhound-ce-python` and to any authenticated domain user |
| Kerberoasting attack executed from Kali | `impacket-GetUserSPNs corp.lab/jsmith -dc-ip 192.168.125.10 -request` run as low-privilege `jsmith` — returned the TGS-REP for `svc_sql` in `hashcat` mode `13100` format, no admin rights or domain-machine foothold required |
| Offline password crack | `rockyou.txt` missed (as expected for a 2009 corpus vs. a newer-style password); a small custom season/year wordlist recovered `Summer2024!` via `hashcat -m 13100` |
| Attack detected in Splunk | `index=main host=DC01 EventCode=4769 Service_Name=svc_sql` returned the exact ticket request: `Account_Name=jsmith@CORP.LAB`, `Client_Address=192.168.125.101` (Kali), `Ticket_Encryption_Type=0x17` (RC4) — full offense-to-detection loop closed on the existing Sysmon \+ Splunk pipeline with no new instrumentation |
| pfSense migration cleanup | Redundant `VMnet8` NAT adapters fully removed from DC01 and `CLIENT01` (not just disconnected) — both VMs now have a single `VMnet1` adapter, routing exclusively through pfSense |
| TrueNAS storage node online | `STORAGE01` (TrueNAS SCALE 25.10.6) built at `192.168.125.40` with a healthy single-disk ZFS pool `tank`, past a VMware duplicate-serial issue resolved via `disk.EnableUUID = "TRUE"` in the `.vmx` and confirmed with `udevadm` |
| TrueNAS AD domain join | `STORAGE01` joined to `corp.lab` under **Credentials → Directory Services** with Kerberos User credentials — Active Directory Status **HEALTHY** after removing a non-AD secondary DNS entry (pfSense) that was breaking SRV lookups |
| SMB share with AD-group ACL | `Sharing` share on `/mnt/tank/shared` with an NFSv4 ACL granting **Modify** to `CORP\operations-staff`, plus the duplicate `shared` entry (case-collision workaround) cleaned up |
| SMB write test as non-admin domain user | `aking` (member of `operations-staff`, not a domain admin) logged in on `CLIENT01`, browsed `\\192.168.125.40\Sharing` over SMB, and created `test.txt` — proving the full AD-group → NFSv4 ACL → SMB share chain end to end |
| TrueNAS syslog into Splunk | TrueNAS syslog forwarded to LOGSRV over UDP `5514` (moved off privileged port `514` after the Splunk service account couldn't bind to it); `source="syslog" index="main" sourcetype="syslog" host=192.168.125.40` returns live, ongoing events |
